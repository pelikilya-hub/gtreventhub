# Деплой GTR Event

## Текущий прод — Cloudflare Workers
**https://gtrevent.com** — собственный домен продукта. Зарегистрирован в
Cloudflare Registrar 27.08.2026, NS Cloudflare, привязан к воркеру как
Custom Domain через `routes` в `wrangler.jsonc`: DNS-запись и сертификат
Cloudflare заводит сам при деплое, руками в панели ничего не делается.

https://gtr-event-hub.gtr-event.workers.dev — технический адрес того же
воркера `gtr-event-hub`, аккаунт `2e3f6f6ab8e81085ca7022ebeb583868`.
Остаётся рабочим: на нём вебхук телеграма, и он выручает, если с доменом
что-то случится. Наружу — гостям, площадкам, артистам — всегда домен.

Адрес приложения живёт в одном месте: `src/gtr/app-url.ts`. Все письма,
кнопки бота и редиректы берут его оттуда — вписывать адрес руками нельзя.

Тариф Workers Free: 100 000 запросов в день, кредитов и карты не требует.

### Что при переезде на домен нужно сделать руками (вне репозитория)
1. **Spotify** — в кабинете разработчика добавить Redirect URI
   `https://gtrevent.com/api/spotify-callback`. Пока не добавлен, вход по
   Spotify отвечает INVALID_CLIENT; ручной выбор жанров работает всегда.
2. **Android (TWA)** — установленный APK собран под старый хост. Ссылки
   на новом домене откроются в браузере, пока приложение не пересобрано
   под `gtrevent.com` (`assetlinks.json` отдаётся тем же воркером, менять
   его не надо).
3. **Телеграм-бот** — вебхук стоит на том адресе, с которого его включали.
   Чтобы перевести бота на домен, откройте BOSS-дашборд **на gtrevent.com**
   и нажмите активацию телеграма: `tgActivateFn` берёт origin текущего
   запроса, поэтому вебхук переедет сам. Со старого адреса бот продолжит
   работать, пока вебхук не переставили.
4. **Почта команды** — логины остались вида `@gtr.events`. Это только
   имена аккаунтов, на работу продукта не влияет; смена логинов — отдельная
   миграция, иначе люди не войдут.

### Выкатка идёт сама из main

`.github/workflows/deploy.yml`: мердж в `main` прогоняет тесты и
выкатывает воркер, потом сверяет отпечаток сборки в проде — молчаливо
«успешный» деплой, не доехавший до воркера, считается провалом.

Нужен один секрет в репозитории: **Settings → Secrets and variables →
Actions → `CLOUDFLARE_API_TOKEN`** (шаблон «Edit Cloudflare Workers»).
Без него выкатка останавливается на первом шаге с понятным текстом.

Почему это появилось: до автоматизации деплой был вот этой ручной
командой, и 30.08.2026 выяснилось, что в проде крутится сборка от 28-го,
а семь смердженных за день работ лежат в main и никуда не едут. Снаружи
это выглядело как «ничего не менялось».

Руками — если надо выкатить с машины, минуя GitHub:

```bash
CLOUDFLARE_API_TOKEN=<токен> CLOUDFLARE_ACCOUNT_ID=2e3f6f6ab8e81085ca7022ebeb583868 \
  npm run deploy:cf
```

`deploy:cf` = сборка (пресет cloudflare_module) + patch-wrangler.mjs
(доклеивает биндинг KV в сгенерированный wrangler.json) + wrangler deploy.

Общая база: Workers KV `gtr-event-store`
(id a26fc466919d43e4a2e684d8765810b8, биндинг GTR_KV) — пользователи
(user:<email>), события (draft:<id>), заявки (req:<id>). Выбирали D1,
но токен «Edit Cloudflare Workers» не имеет прав на D1 — KV входит в
шаблон. Для переезда на D1: добавить в токен право D1:Edit.

Токен — аккаунт-токен (`cfat_…`), создан по шаблону «Edit Cloudflare Workers».
В репозитории его не храним; проверка живости:
`curl https://api.cloudflare.com/client/v4/accounts/<acc>/tokens/verify -H "Authorization: Bearer <токен>"`.

Секреты воркера уже заданы (`wrangler secret put <NAME> --name gtr-event-hub`):
GTR_ACCESS_PASSWORD (пароль стенда), GTR_SESSION_SECRET (подпись сессий).
process.env в воркере наполняется автоматически: nodejs_compat +
compatibility_date ≥ 2025-04-01.

Имя воркера передаём флагом `--name`: сгенерированный
.output/server/wrangler.json называет его `pelikilya-hub-gtreventhub`.

## Из песочницы Claude Code
Node fetch не видит HTTPS_PROXY — перед деплой-командами ставить
`NODE_USE_ENV_PROXY=1` (подробнее в README). Свежесозданный поддомен
workers.dev поднимает TLS-сертификат несколько минут — «handshake failure»
сразу после первого деплоя это норма, просто подождать.

## Telegram: где живут фирменные эмодзи, а где нет

Наш пак кастомных эмодзи (`BRAND_EMOJI` в `src/gtr/tg.ts`) работает не везде —
это ограничение Telegram, а не наш код. Проверено вживую 27.08.2026 на
@Gtrcom1_bot:

| Куда | Результат |
|---|---|
| Личка боту (`sendMessage`, HTML) | работает — в ответе три `custom_emoji` |
| Вопрос опроса (`question_parse_mode: "HTML"`) | работает — `question_entities: custom_emoji` |
| Пост в канал @gtr_live | **вырезаются** — сущностей в посте нет вовсе |
| Реакция кастомным эмодзи (`setMessageReaction`) | **REACTION_INVALID** |

Кастомные эмодзи в постах канала Telegram открывает только после бустов —
пока бустов нет, канал показывает обычный знак-подложку. Поэтому вопросы
опросов начинаются именно с того знака, который есть в карте `BRAND_EMOJI`:
`brandEmojify` подменяет его по точному совпадению, а без пака остаётся
читаемый обычный эмодзи. Сторож — блок «фирменный слой» в
`src/gtr/__tests__/community-marketing.test.ts`.

Реакции кастомным эмодзи не пытаться чинить: Bot API принимает в
`setMessageReaction` только эмодзи из фиксированного списка Telegram.
