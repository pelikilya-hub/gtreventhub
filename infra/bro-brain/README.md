# Мозг GTR BRO на Hetzner (8 vCPU / 16 ГБ)

Самохостный текстовый мозг: Qwen3-8B (Apache 2.0) через llama.cpp (MIT).
Запасной путь текстового чата: когда Gemini недоступен или упёрся в
квоту, отвечает он. Ни одного запроса к платным API.

## Запуск — одна команда

Скопируй на сервер `setup-brain-vps.sh` из этой папки и запусти от root:

```bash
sudo bash setup-brain-vps.sh
```

Скрипт сам ставит Docker, определяет публичный IP, поднимает модель и
Caddy с TLS, дожидается ответа и печатает URL с токеном. Повторный
запуск ничего не ломает: токен и скачанная модель переиспользуются.

### Почему адрес постоянный

Раньше мозг жил на quick-туннеле `trycloudflare.com`. Тот выдаёт новый
адрес при каждом перезапуске, а старый перестаёт резолвиться — воркер
получал `530 error code: 1016`, и мозг молча пропадал из продукта.

Теперь имя привязано к IP сервера через [sslip.io](https://sslip.io):
публичный DNS резолвит `1-2-3-4.sslip.io` в `1.2.3.4`. Имя настоящее,
сертификат Let's Encrypt на него выдаётся штатно, домен покупать не
нужно. Пока у сервера тот же IP — адрес живёт вечно.

**Условие:** открытые порты 80 и 443. Порт 80 нужен Let's Encrypt для
проверки владения именем, 443 — рабочий. Порт модели (8080) наружу не
смотрит вовсе: он остаётся внутри docker-сети, снаружи только Caddy.

## Проверка

```bash
# снаружи, по постоянному адресу
curl -s https://<ip-через-дефисы>.sslip.io/v1/chat/completions \
  -H "Authorization: Bearer <токен>" -H 'content-type: application/json' \
  -d '{"model":"qwen3-8b","messages":[{"role":"user","content":"Скажи одно слово: эфир"}],"max_tokens":10}'
```

## Подключение к продукту

KV-ключ `setting:brain` в неймспейсе GTR:

```json
{ "url": "https://<ip-через-дефисы>.sslip.io", "token": "<токен>", "model": "qwen3-8b" }
```

Вписывается на стенде `/bro-dev` → Настройки → «Запасной мозг», либо
Claude вписывает сам через пульт (`pult.brain`). Убрать ключ — текстовый
чат останется на одном Gemini.

Живое состояние мозга видно в `GET /api/gtr-bro-session` в поле
`brainProbe`: `health` и `models` должны отвечать без ошибки.

**Но brainProbe не проверяет токен.** У llama.cpp `/health` и
`/v1/models` открыты без авторизации, поэтому два зелёных ответа не
доказывают, что токен в KV совпадает с токеном на сервере. Настоящая
проверка — запросом с `Authorization`:

```bash
curl -sS -X POST https://gtr-event-hub.gtr-event.workers.dev/api/bro-dev \
  -H 'content-type: application/json' \
  -d '{"action":"pult.brainTest","key":"<ключ пульта>"}'
```

`401` — токен разошёлся с `/opt/bro-brain/.env`, `200` — всё сходится.
Спрашивается одно слово (`max_tokens: 8`), слот инференса занят недолго.

## Почему мозг больше не отваливается молча

Три независимых слоя, каждый закрывает свой вид отказа.

1. **Адрес.** Раньше был quick-туннель `trycloudflare.com` — он протухает
   сам по себе, и однажды протух. Теперь имя завязано на IP сервера через
   sslip.io: оно не истекает, пока жив сам сервер.
2. **Процесс.** `restart: unless-stopped` поднимает упавший контейнер и
   переживает перезагрузку сервера. Зависший процесс так не вылечить —
   для него healthcheck на `/health` плюс сайдкар `autoheal`, который раз
   в минуту перезапускает помеченное unhealthy.
3. **Тишина.** Крон `/api/brain-watch` в воркере проверяет мозг каждые
   15 минут и на отказе кладёт запись в очередь пульта, а на возврате —
   вторую. По одной записи на переход: сторож, повторяющий одно и то же
   каждые четверть часа, учит не чинить, а не читать.

   Проб две. Сперва `/health` — дёшево, без инференса. Потом настоящий
   запрос с токеном и `max_tokens: 1`. Вторая обязательна: `/health` и
   `/v1/models` у llama.cpp открыты без авторизации, поэтому при
   разошедшихся токенах обе отвечают `200`, а рабочий запрос получает
   `401`. Сторож на одном `/health` рапортовал бы «всё хорошо» над
   мозгом, которым продукт не может воспользоваться.

   Недоступность требует двух промахов подряд — сеть до Hetzner моргает,
   а холодный инференс отвечает не сразу. `401` будит с первой пробы:
   разошедшаяся настройка не транзиентна и сама не рассосётся.

Третий слой здесь главный. Первые два чинят поломку, но прошлый отказ
прожил пять дней не потому, что его не могли починить, а потому что
смотреть на него было некому: продукт молча откатывался на Gemini и
разбор правилами, и снаружи всё выглядело рабочим.

## Обновить уже запущенный сервер

```bash
sudo bash setup-brain-vps.sh   # тот же скрипт, модель не перекачивается
```

## Что важно знать

- **Параллельные гости.** Сервер держит 3 слота одновременно
  (`--parallel 3`) — раньше без этого флага второй одновременный
  вопрос вставал в очередь и часто не успевал за 26-секундный дедлайн
  воркера («упёрлись в лимиты», хотя это не лимит Gemini, а очередь
  на один слот). Три слота — это именно то, ради чего есть VPS вместо
  домашнего GPU: тот всегда обслуживал один запрос за раз.
- Контекст 12288 делится между слотами поровну: 4096 на слот — хватает
  на системный промпт с инструментами и пару кругов вызовов.
- Первый ответ после старта медленный (прогрев кэша промпта), дальше
  системный префикс закэширован и отвечает за секунды.
- Таймауты в Caddy намеренно не заданы: у него по умолчанию их нет, а
  модель на CPU отдаёт заголовки ответа только в конце генерации. Срок
  ответа держит воркер (26 секунд) — он тут единственный судья.
- Обновление модели: поменять `LLAMA_ARG_HF_REPO` в `docker-compose.yml`
  на сервере, затем `docker compose up -d`.
- Голосовую связку (Whisper + Chatterbox) этот сервер не потянет: синтез
  речи на CPU медленнее самой речи. Для голоса — либо баланс OpenAI,
  либо GPU-сервер.
- Если IP сервера сменится (переезд, пересоздание VPS) — просто запусти
  скрипт заново: он вычислит новое имя и переиздаст сертификат. Не забудь
  переписать `setting:brain`: сторож заметит смену адреса и поднимет
  тревогу, но починить её за тебя не сможет.
- `autoheal` получает доступ к `docker.sock`, то есть право управлять
  контейнерами хоста. Это цена автолечения — держи в уме, если на сервер
  приедет что-то ещё.

## Домашний GPU (Windows + NVIDIA)

`gpu/setup-brain-gpu.ps1` — тот же мозг, но на видеокарте. Разница с
CPU-сервером принципиальная: Qwen3-8B на GPU отвечает за доли секунды
вместо двух, и только с ним имеет смысл включать `brainFirst` — свой
мозг основным, а не запасным.

```powershell
powershell -ExecutionPolicy Bypass -File .\setup-brain-gpu.ps1
```

Скрипт сам определяет объём видеопамяти и по нему выбирает число слотов
и контекст: 16 ГБ и больше — три слота по 4096, 11 ГБ — три по 3072,
8 ГБ — два, меньше — один со честным предупреждением, что второй гость
встанет в очередь.

### Постоянный адрес и здесь

При первом запуске скрипт предлагает войти в Cloudflare и поднимает
**именованный** туннель на `brain.gtr.events`. Адрес не меняется никогда
— ни при перезапуске, ни при перезагрузке компьютера.

Отказаться можно: тогда будет quick-туннель `trycloudflare.com`, но он
выдаёт новый адрес при каждом запуске, а старый перестаёт резолвиться.
Ровно на этом мозг однажды пропал из продукта на пять дней.

### Чего у CPU-сервера нет, а тут нужно

- **Автозапуск.** Домашний компьютер перезагружают. Скрипт регистрирует
  задачу «GTR BRO brain» на вход в систему, иначе после каждой
  перезагрузки мозг офлайн, и узнаём мы об этом от гостя.
- **Ожидание готовности.** Туннель, поднятый раньше модели, отдаёт 502:
  адрес есть, мозга нет. Скрипт ждёт `/health`, прежде чем открывать
  дверь наружу.
- **`--jinja`.** Без него шаблон Qwen3 для вызова инструментов не
  разворачивается, и мозг не может ни искать афишу, ни бронировать
  стол — он просто болтает. В прежней версии скрипта флага не было.

### Что домашний GPU не отменяет

Компьютер выключен — мозг офлайн. Поэтому Gemini остаётся страховкой, а
`brainFirst` меняет порядок движков, но не выбрасывает запасной.

## Старый вариант

`docker-compose.yml` в этой папке — схема без TLS (порт 8080 наружу,
plain HTTP). Именно она сейчас крутится на VPS. Новые установки с нуля
делай `setup-brain-vps.sh` — он добавляет Caddy и TLS.
